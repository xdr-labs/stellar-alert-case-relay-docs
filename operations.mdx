---
title: "Run continuously with systemd"
description: "Install, start, verify, and operate the relay as a systemd service."
---

The wizard-enabled relay can create and manage its own systemd service. Manual unit creation is no longer the recommended installation path.

## Install from the wizard

Run:

```bash
python3 Stellar_Alert_Case_Syslog.py --setup
```

Complete the Alert/Case configuration and answer **Yes** when prompted:

```text
Run continuously with systemd (auto-start on boot)?
```

Administrator privileges are required. If the current shell is not root, the script runs sudo and may ask for your password.

## Files installed

The wizard creates or updates:

```text
/usr/local/lib/stellar-alert-case/Stellar_Alert_Case_Syslog.py
/etc/default/stellar-alert-case-syslog
/etc/systemd/system/stellar-alert-case-syslog.service
```

The token environment file is written with mode `0600`.

The generated service uses the user who invoked the wizard, preserves that user's home directory for the default SQLite/log paths, and includes:

```ini
Restart=always
RestartSec=5
UMask=0077
```

The API token is loaded through:

```ini
EnvironmentFile=-/etc/default/stellar-alert-case-syslog
```

and is not included in `ExecStart`.

## What installation does

The installer runs the equivalent of:

```bash
sudo systemctl daemon-reload
sudo systemctl enable stellar-alert-case-syslog
sudo systemctl restart stellar-alert-case-syslog
```

It then displays:

- Full service status
- The most recent 20 journal entries
- Active-state verification
- Enabled-state verification

A successful installation ends with a message that the service is both active and enabled.

## Check status

```bash
sudo systemctl status stellar-alert-case-syslog
```

Check both runtime and boot state:

```bash
systemctl is-active stellar-alert-case-syslog
systemctl is-enabled stellar-alert-case-syslog
```

## Follow logs

```bash
sudo journalctl -u stellar-alert-case-syslog -f
```

Recent logs only:

```bash
sudo journalctl -u stellar-alert-case-syslog -n 50 --no-pager
```

The journal should be reviewed after installation to confirm that API fetching and TCP delivery are actually succeeding; an active process alone does not prove end-to-end delivery.

## Restart

```bash
sudo systemctl restart stellar-alert-case-syslog
sudo systemctl status stellar-alert-case-syslog
```

## Reconfigure

Run the wizard again:

```bash
python3 Stellar_Alert_Case_Syslog.py --setup
```

Choose the new values and answer **Yes** to systemd installation. The script replaces the installed script/configuration, reloads systemd, and restarts the service.

## Inspect the installed configuration

View the unit:

```bash
systemctl cat stellar-alert-case-syslog
```

Do not print the token file into shared logs or support tickets. It contains the API credential.

## Runtime state

Because the service runs as the invoking user and sets that user's `HOME`, the default persistent state remains under:

```text
~/.local/state/stellar_alert_case/
```

This includes the SQLite queue/checkpoints, process lock, and relay logs.

## Receiver outage behavior

If a destination TCP listener becomes unreachable, queued unsent data is retained. The relay enters its retry/recovery path instead of marking those records as sent.
