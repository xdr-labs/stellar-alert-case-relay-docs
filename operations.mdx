---
title: "Run continuously with systemd"
description: "Keep the relay running at boot, recover from failures, and inspect service logs."
---

The operational guide recommends running the relay as a `systemd` service so it starts with the host and can recover automatically from process failures.

## Create the service unit

Create:

```text
/etc/systemd/system/stellar-alert-case.service
```

The guide uses the following deployment example:

```ini
[Unit]
Description=Stellar Cyber Alert + Case Syslog daemon
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=aella
Group=aella
WorkingDirectory=/home/aella/kt
ExecStart=/usr/bin/python3 /home/aella/kt/Stellar_Alert_Case_Syslog.py \
  --alert-interval 60 \
  --case-interval 3600 \
  --alert-syslog-ip 10.10.10.20 \
  --alert-syslog-port 5201 \
  --case-syslog-ip 10.10.10.20 \
  --case-syslog-port 5142 \
  --case-include-summary \
  --no-case-format-summary \
  --case-fetch-timeout 90
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

<Warning>
The user, group, working directory, script path, destination addresses, and ports above are examples from the operational guide. Change them to match your environment.
</Warning>

## Enable and start the service

After writing or changing the unit file, use the standard systemd workflow:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now stellar-alert-case.service
sudo systemctl status stellar-alert-case.service
```

To restart it after a configuration change:

```bash
sudo systemctl restart stellar-alert-case.service
```

## Follow service logs

```bash
journalctl -u stellar-alert-case.service -f
```

To inspect the effective unit file:

```bash
systemctl cat stellar-alert-case.service
```

## Recovery behavior

The guide explicitly recommends:

```ini
Restart=on-failure
RestartSec=10
```

This allows `systemd` to restart the daemon after a process failure while avoiding an immediate tight restart loop.

The product overview also identifies these relay capabilities as being designed for real operations:

- Fetch checkpointing
- Send retry/recovery
- Backfill
- Separate alert and case destinations

<Note>
The current guide names checkpoint, retry/recovery, and backfill as capabilities but does not define their persistence format, retry schedule, retention window, duplicate-handling behavior, or backfill controls. Those implementation details require verification against the runtime source.
</Note>

## Operational tips

- Use `Restart=on-failure` for automatic process recovery.
- Use `--debug` only when troubleshooting.
- Verify TCP reachability from the relay host to every configured destination.
- Keep alert and case destinations separate when downstream workflows require independent ingestion paths.
- After changing command-line options in the unit file, run `daemon-reload` before restarting the service.
