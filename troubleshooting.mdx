title: "Troubleshooting"
description: "Check stream configuration, systemd state, and TCP NDJSON delivery."
---

Start with configuration completeness. The relay treats alert and case streams independently, and a partially configured stream is an error.

## A stream will not start

Verify that all required settings for the affected stream are present.

### Alert stream

```text
--alert-interval
--alert-syslog-ip
--alert-syslog-port
```

### Case stream

```text
--case-interval
--case-syslog-ip
--case-syslog-port
```

If every option for a stream is omitted, that stream is disabled. If configuration for a stream is started but one of its required options is missing, the guide says that stream is an error.

## The service is not running

Check the unit state:

```bash
sudo systemctl status stellar-alert-case.service
```

If you recently edited the unit file:

```bash
sudo systemctl daemon-reload
sudo systemctl restart stellar-alert-case.service
```

Follow the service journal while reproducing the problem:

```bash
journalctl -u stellar-alert-case.service -f
```

The guide recommends `Restart=on-failure` and `RestartSec=10` for automatic recovery.

## The receiver gets no records

Check the path from the relay host to the configured destination:

1. Confirm the destination IP and port are correct for the affected stream.
2. Confirm the receiver is listening on that TCP port.
3. Confirm network policy or firewall rules allow the relay host to connect.
4. Confirm the receiver expects newline-delimited JSON rather than traditional syslog framing.
5. Confirm that the corresponding alert or case stream is fully enabled.

## The receiver cannot parse records

The documented wire format is one JSON object per line over TCP.

```text
JSON object + newline
JSON object + newline
...
```

The guide does not provide a complete JSON schema. Validate parsing against real output before creating field mappings in a SIEM or SOC portal.

## Case fetching needs investigation

The guide's recommended case example includes:

```bash
--case-fetch-timeout 90
```

It also recommends:

```bash
--case-include-summary
--no-case-format-summary
```

The exact timeout units and the complete semantics of the summary-formatting flags are not described in the available guide, so verify those behaviors against the runtime source before changing them for production.

## Debugging

The operations guide says to use `--debug` only when troubleshooting.

<Warning>
Do not leave debug mode enabled indefinitely in production unless the runtime implementation has been reviewed for log volume and sensitive-data handling.
</Warning>

## What still requires source verification

The available guide is enough to document basic deployment and operation, but it does not define all implementation behavior. Source verification is still required for:

- Stellar Cyber API authentication and endpoint configuration
- Full CLI option list, defaults, and numeric units
- Fetch checkpoint location and persistence semantics
- Retry schedule and duplicate-handling behavior
- Backfill configuration and limits
- Alert/case JSON schemas and discriminator fields
- Case summary transformation semantics
- Log file destinations beyond the systemd journal

Once the runtime source is available in GitHub, these items can be converted from caveats into exact reference documentation.
